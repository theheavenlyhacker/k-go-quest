# Expo SQLite integration contract

The central backend uses PostgreSQL. SQLite belongs in the Expo app and does not connect directly to Aiven. This document specifies the client contract; this repository does not implement or change the mobile app.

1. Sign in online with loginId, password, and a persistent random deviceId. Store access and refresh tokens in SecureStore. GET classrooms gives the learner's active memberships.
2. GET content/packs with the classroom grade and desired subject. Download each published pack with content/packs/:id/download. Verify checksum as SHA-256 of JSON.stringify({ pack: response.pack, lessons: response.lessons }); downloadedAt and other response metadata are excluded. Save the whole immutable version atomically in SQLite. Media downloads and on-device models are separate integrations.
3. Store each selected answer in a local outbox before changing screens. Use a new UUID clientAttemptId and persist the exact classroomId, exerciseId, selectedOption, and UTC occurredAt. Scope cached profiles, progress, and outboxes by authenticated student ID. Preserve events across app restarts and connection loss.
4. When online, POST learning/sync in batches of at most 100. Never submit correctness, coins, mastery, role, or studentId. Server grading is authoritative. Downloaded packs have gradingMode SERVER_ON_SYNC and no answer keys; the app cannot claim authoritative correctness while offline.
5. After a successful response, transactionally acknowledge only IDs present in results and replace the confirmed wallet with coinBalance. Keep the exact event ID/payload after timeouts or a lost response. Duplicate events do not earn again. Top-level awardedCoins counts only newly earned coins; an individual duplicate result describes its original award.
6. Pull learning/progress/me, learning/quests, and classrooms after sync. Keep confirmed progress separate from pending practice. This version offers snapshots through these endpoints, not a general cursor-based replication feed.

Suggested SQLite tables: `pack_cache(packId PRIMARY KEY, version, checksum, payloadJson, cachedAt)`, `profile_cache(studentId PRIMARY KEY, payloadJson, refreshedAt)`, and `attempt_outbox(studentId, clientAttemptId, classroomId, exerciseId, selectedOption, occurredAt, state, lastError)` with primary key `(studentId, clientAttemptId)`. Do not store credentials in these tables. Plain SQLite is not encryption; shared-tablet PINs, inactivity locks, encrypted storage, and cache access enforcement must be implemented in Expo before real student deployment.

Retry network failures, 429 responses, and 5xx responses with bounded exponential backoff and jitter. On 401, serialize a refresh request using the same deviceId; retain the outbox when sign-in is required. The server rotates refresh tokens, so concurrent refresh attempts must share one in-flight operation. Never interpret a permission error as a successful upload.

Validation and authorization failures roll back the entire batch. To identify a bad item, retry smaller batches down to one item, preserve its original payload, and mark that item for review with the reason. Do not discard unsynced learning silently. A changed payload under an existing UUID receives 409; retain it for investigation. New events older than 30 days, events more than five minutes in the future, wrong-grade exercises, and inactive memberships are rejected. Previously committed identical events can still be acknowledged after that upload window or enrollment ends.

Rewards require an online request and sufficient confirmed coins. Persist a UUID requestId before submitting redemption and reuse it on retries. Vouchers are claimed online by the owning LGU. Neither client-reported coin deltas nor offline voucher spending is accepted.

This NestJS API uses camelCase and `/api/v1` routes. The separate Express app's `/v1/sync/push`, device-token enrollment, client coin events, and snake_case payloads are a different protocol and are not compatible without an explicit client migration.
